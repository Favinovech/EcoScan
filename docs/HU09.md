# HU09 — Recordatorios y sincronización

## Cómo cumple cada criterio

| Criterio | Archivo principal |
|---|---|
| WorkManager programa el recordatorio periódico según el distrito | `data/reminder/ReminderScheduler.kt` calcula el retraso inicial con `domain/schedule/ReminderTimeCalculator.kt` (función pura, zona `America/Lima`) y encola un `PeriodicWorkRequest` cada 7 días con `ExistingPeriodicWorkPolicy.UPDATE`, así que cambiar de distrito reprograma en vez de duplicar. |
| Sincronización automática de escaneos/reportes pendientes, con restricción de red | `data/sync/SyncScheduler.kt` encola `SyncWorker` con `NetworkType.CONNECTED`; `WasteRecordSyncCoordinator.kt` sincroniza también mientras la app está abierta (login, reconexión, cambios locales). `WasteRecordSyncerImpl.kt` y `ProfileRepositoryImpl.kt` escriben en Firestore (y Storage, si hay foto) **antes** de marcar `isSynced = true`, nunca al revés. |
| Notificaciones push (FCM) para campañas y logros | `data/notification/EcoScanMessagingService.kt` recibe los mensajes de los topics `campanas` y `logros`; `NotificationTopicManager.kt` suscribe/cancela esos topics según el interruptor maestro del perfil. |
| Alerta sonora y vibración configurables desde el perfil | `domain/preferences/NotificationPreferences.kt` + `data/preferences/DataStoreNotificationPreferences.kt` guardan la preferencia; `domain/notification/NotificationChannelSelector.kt` (función pura) elige uno de los 4 canales fijos creados en `NotificationChannels.kt`; se edita en `ProfileScreen.kt`. |
| Política de reintento con backoff exponencial | `data/sync/SyncScheduler.kt` usa `BackoffPolicy.EXPONENTIAL`; `data/sync/SyncErrorClassifier.kt` clasifica la excepción real (red/Firestore) como transitoria o permanente; `domain/sync/RetryPolicy.kt` (función pura) decide reintentar o fallar según ese tipo **y** el número de intento, con un tope (`MAX_SYNC_ATTEMPTS = 5`) para no reintentar indefinidamente un error transitorio que nunca se resuelve. |

Las decisiones de las 5 áreas están en funciones puras con pruebas JUnit (`ReminderTimeCalculatorTest`, `SyncErrorClassifierTest`, `RetryPolicyTest`, `NotificationChannelSelectorTest`, `PushNotificationContentTest`); la orquestación de cada Worker (`SyncWorkerTest`, `ReminderWorkerTest`) se prueba en androidTest con `TestListenableWorkerBuilder`.

## Consola de Firebase

- **Topics FCM**: `campanas` y `logros`. No se crean en la consola; un dispositivo se suscribe/cancela solo al cambiar el interruptor de notificaciones del perfil. Las campañas y logros se envían manualmente desde *Cloud Messaging → Enviar mensaje de prueba* (o a la API), eligiendo el topic correspondiente.
- **Reglas de Firestore**: deben restringir `users/{uid}/**` (perfil y `waste_records`) al propio usuario autenticado. Texto sugerido (pendiente de pegar en la consola, no vive en el código):

```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /users/{uid} {
      allow read, write: if request.auth != null && request.auth.uid == uid;
      match /waste_records/{recordId} {
        allow read, write: if request.auth != null && request.auth.uid == uid;
      }
    }
    match /{document=**} {
      allow read, write: if false;
    }
  }
}
```

- **Queda manual**: pegar esa regla en la consola (no en modo prueba), y enviar las campañas/logros desde la consola o un backend propio — esta app no tiene servidor que dispare notificaciones.

## Limitaciones

- WorkManager no garantiza la hora exacta: Doze y el ahorro de batería pueden retrasar la ejecución del recordatorio.
- Con la app en segundo plano, un mensaje FCM con bloque `notification` lo muestra el sistema directamente con el canal por defecto (`ecoscan_sonido_vibracion`), sin pasar por `EcoScanMessagingService`.
- Los horarios de recolección por distrito (`CollectionScheduleRepositoryImpl`) son ilustrativos; los reales los define la asociación de recicladores, no esta app.
- El permiso `POST_NOTIFICATIONS` (Android 13+) no se pudo probar en el dispositivo de prueba (Moto G9 Power, Android 11), donde las notificaciones no requieren permiso en tiempo de ejecución.
- Los reportes comunitarios de HU08 (rama `feature/HU08-reportes-comunitarios`) no están en esta rama. Se revisó su código en esa rama por separado: si el reporte lleva foto y no hay red, la subida a Firebase Storage falla y el reporte completo se pierde (no hay cola offline para Storage, y el documento de Firestore nunca se llega a escribir porque la subida de la foto va primero en la misma operación). No se corrigió aquí porque el archivo no existe en esta rama.
